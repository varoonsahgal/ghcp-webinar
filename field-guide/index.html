Chapter 01 · Ground school

Start here

What you'll build, the two codebases you'll work in, and the one question every chapter keeps asking.

The one question

Whole course

How much control should I hand to the AI for this task, and which controls should I never hand over?

Not long ago, "using Copilot" meant typing a question into a chat box. Now Copilot can edit dozens of files, run your build, spawn helpers that work in parallel and open a pull request. Every one of those powers is optional. The skill this lab teaches is picking the right amount for each job, and writing down the rules that hold no matter how much you hand over.

You are the pilot in command. Copilot is the co-pilot.

Tidbit

The name is more apt than it looks. In aviation the pilot in command is legally responsible for the flight even while the first officer is flying the aircraft. Handing over the controls never hands over the responsibility. The same holds for code an agent writes on your machine and pushes under your name.

Chapter 02 · Ground school

Harness, agent, model

Three separate dials that people blur into one word, "Copilot". Keeping them apart explains most of what surprises people.

The three dials

Part 0

The model is the brain. The agent is the role it plays. The harness is the engine that runs the loop, applies permissions and calls tools.

  • Model: a specific model, Auto (Copilot picks per request), or HydraFusion (a research preview that mixes models for you).
  • Agent: Ask, Plan, Agent, or a custom agent like the Tech Lead. An agent is a persona plus a tool list plus, optionally, a model and hooks.
  • Harness, chosen with Session Target: Local (VS Code's built-in loop, used all day today), Copilot (the runtime shared with Copilot CLI and the Copilot app), Claude and Codex (the vendors' own harnesses), and Cloud (runs remotely and comes back as a PR).

The agent loop

Foundations

A model on its own only writes text. It can't open a file or run mvn. An agent works because the harness offers the model a menu of tools (read, search, edit, execute, start a subagent). When the model's reply is a request to use one, the harness checks the rules, runs it, and feeds the result back in. The loop repeats until the model answers in plain text.

Why the harness matters

Part 0 · Part 2

Hooks, tool names and some customization features are harness-specific. A hook written for Local uses events like PreToolUse and fields like tool_name; the Copilot harness and Copilot CLI read the same .github/hooks/*.json files but have their own event list (agentStop, errorOccurred…). That is why the lab pins Session Target → Local.

Analogy

The model is a brilliant contractor who can only talk. The harness is the site office: it hands out the tools, keeps the sign-in sheet, and enforces site rules. The agent is the job title on the badge. Swap the contractor and the site rules stay the same. Move to a different site office and the rules change, even with the same contractor.

The Agents window

Part 0 · Part 3

A separate VS Code window built for assigning and reviewing agent work across many sessions, rather than chatting in one.

Open it with Open in Agents in the title bar or code --agents. It adds worktrees, Dev Containers, Automations (scheduled prompts), a Changes panel, Create PR and the experimental Agent merge. Sessions are shared with the normal Chat view, so you can start in one and finish in the other.

Weekly releases

Part 0

VS Code now ships every week (1.136 to 1.140 all landed in September 2026). Screens in any guide, including this one, drift quickly. Update on the morning of class with Help → Check for Updates, and when a menu doesn't match, search the Command Palette (⇧⌘P / Ctrl+Shift+P) for the command name.

Tidbit

Edit mode was deprecated, then removed in 1.126 (June 2026). It isn't gone so much as absorbed: Ask, Plan and Agent are themselves just custom agents with different tool lists. If you want a "constrained editor", you write one.

Chapter 03 · Ground school

Tokens & AI Credits

Since June 1, 2026 you pay for what the model reads and writes, not for how many times you press Enter. That changes which habits are cheap.

Tokens

Part 0

Models read and write in tokens, chunks of text roughly ¾ of an English word long. Under GitHub AI Credits, each model has its own price per token.

Analogy

The old premium-request model was a bus ticket: one fare per ride, however far you went. AI Credits is a taxi meter: it runs for the whole trip, and every detour shows up on the fare. A 40-step agent loop that rereads the same five files is a long detour.

What actually drives cost

Part 0 · Part 1
  • The whole context is re-sent every turn. In a 30-turn agent loop, the instructions and file contents from turn 1 are paid for again on turns 2 to 30. Prompt caching makes repeats cheaper, not free.
  • Tool results pile up. Test logs, file reads and terminal output usually outweigh everything you typed.
  • Every enabled tool costs tokens on every turn. Tool definitions are part of the fixed overhead, so an unused MCP server with 40 tools isn't free.
  • Subagents multiply. Each one has its own context and its own bill. They are worth it when they keep noise out of the main thread, not by default.

The levers you control

Part 0
LeverHow
Use AutoAuto is 10% cheaper than choosing the same model directly. Set Optimize for → Efficiency for routine work.
Lower rungAn Ask turn that answers in one shot uses a fraction of an Agent turn's tokens. See Chapter 04.
Smaller context#file instead of "look at everything", /compact, a new session per task.
Cheaper workersGive read-only recon subagents a small, fast model with model: in their agent file.
Trap

The old "use a 0x model" trick is gone. Nothing is free per prompt any more, so "just let Agent figure it out" now has a visible price. Check Session Cost after each lab step and compare.

Tidbit

"Taxi" is short for taximeter cab. The taximeter (from Greek taxa, charge) was invented in Germany in 1891, decades before the cars it ended up in. Metered billing is old; it's just new to your IDE.

Chapter 04 · Part 1

The autonomy ladder

Ask, Plan, Agent, Autopilot, a squad, the cloud. Each rung buys speed with tokens and trust. Choosing the lowest rung that gets the job done is the skill.

Autonomy is a dial, not a switch

Part 1

Each rung gives the AI more freedom to act without asking you, and needs more guardrails to be safe.

Analogy

Ask is a passenger giving directions. Agent is a learner driver: they hold the wheel, you sit beside them with your own brake and approve each turn onto a main road. Autopilot is letting them drive alone. Nobody hands the keys over on day one, and nobody hands them over on an icy night without good brakes fitted. Hooks and checkpoints are those brakes.

Tidbit

Self-driving cars use the same idea. The SAE J3016 standard defines six levels, from 0 (no automation) to 5 (drives anywhere, no human needed). Most cars on the road today sit at level 2: the car steers and brakes, the human watches all the time.

#RungWhat it doesUse it when
1AskRead-only tools. One bounded answer. Nothing loops.Explaining, exploring, a one-shot answer or a scaffold to preview.
2PlanResearches the codebase, asks clarifying questions, writes plan.md.The change is risky or you aren't sure what you want yet.
3AgentEdits files, runs commands, reads errors, fixes its own mistakes. You approve tools.Multi-step work you can verify, for example with a build or tests.
4AutopilotAgent with tool approvals switched off. Keeps going until done.Hooks and checkpoints have your back, and your org allows it.

Ask is "just" a custom agent

Part 1 · Step 1

Hover Ask in the agents dropdown and open its definition (or type /agents). It literally introduces itself as an agent ("You are an ASK AGENT…") and has only read-only tools. The built-in agents are examples of the same file format you'll use for the Tech Lead in Part 3.

/new in Ask scaffolds a whole project from a sentence and shows you a preview first. One bounded pass: it proposes, you accept or not. Nothing self-corrects. That's the point of the lowest rung.

Is Agent overkill?

Part 1 · Discussion

An Agent turn can run 10 to 40 tool calls, rereading files and test output each time. An Ask turn that answers in one go uses a fraction of that. Under token billing, Ask with good context is often genuinely cheaper, not just "fewer prompts". Reach for Agent when the work needs doing, not just knowing.

More autonomy is not always better.

Approvals and the risk assessment

Part 1 · Step 3

With Default Approvals, Agent asks before running terminal commands, and each request comes with an AI risk assessment that says what the command does in plain words ("executes remote code"). Read it. It's a second opinion, not a guarantee.

Steer vs. queue

Part 1 · Step 4

While an agent is working you can type a follow-up and choose how it lands.

  • Steer injects your message into the run that's happening now. Use it to correct course ("make Celsius the default").
  • Queue waits until the current turn finishes, then sends. Use it for the next task.
  • Stop and send cancels the run and starts fresh with your message.
Analogy

Steering is the navigator saying "next left, not right" while you're still driving. Queueing is adding a stop to the trip. Stopping is pulling over.

Tidbit

The lab calls Agent "a fast junior engineer". A 2025 METR study is a useful reality check: 16 experienced open-source developers were measured as 19% slower on real tasks when allowed AI tools, while they believed they had been about 20% faster. Agents can feel productive without being productive. Measure, don't assume. That's what Part 3's logs are for.

Chapter 05 · Part 1

Precise context

Before you reach for a bigger agent or a bigger model, give the one you have better information.

Context items: the # menu

Part 1 · Step 2

Typing # in chat lets you attach exactly the information the model needs, instead of hoping it goes looking for it.

ItemWhat it attaches
#terminalSelectionThe exact text you highlighted in the terminal, such as a stack trace.
#problemsThe compiler and linter errors from the Problems panel.
#changesYour uncommitted Git changes.
#<file>, #<symbol>One file, or one class or method.

Analogy

Telling a doctor "it hurts somewhere" gets you a long examination. Pointing to the spot and handing over the X-ray gets you a diagnosis. #terminalSelection is the X-ray.

Ask plus great context beats Agent plus vague context.

Inline chat

Part 1 · Step 2

Select some code and press ⌘I / Ctrl+I. The suggestion appears in place, as a diff you accept or discard. It's the smallest and cheapest context there is: the selection, the file, and your one sentence. Perfect for a one-spot fix.

Chapter 06 · Part 1

The context window

The model has no memory between calls. Everything it "knows" right now is whatever the harness packed into this one request.

Context and the context window

Part 1 · Step 5

The context is everything the model sees on a turn. The context window is the most it can hold at once, measured in tokens.

A fresh chat "doesn't know" what you discussed in another chat, and a subagent doesn't know what its parent discussed with you, for the same reason: neither was in the context. If something must survive, it has to be written down somewhere that gets loaded, such as an instructions file, a skill or a plan file.

Analogy

The context window is a desk, not a filing cabinet. A bigger desk lets you spread out more papers, but you still read them one glance at a time. Pile on enough old drafts and stack traces and you start working from the wrong page.

The ring

Part 1 · Step 5

The small ring with a percentage at the bottom-right of the chat input is the context window control. Hover or click it.

In the popupWhat it tells you
Session CostAI Credits spent in this session so far.
Context WindowHow much of the window this request uses, for example 26.1K / 1M. The shaded part is reserved for the reply.
SystemInstructions and tool definitions. Fixed overhead on every turn.
User ContextMessages and tool results. The part that grows. In agent loops, tool results usually dominate.
Compact ConversationSummarizes older history to free space.

The six layers

Part 1 · Step 5
  1. System instructions: the agent's own prompt and tool definitions.
  2. Custom instructions: copilot-instructions.md and matching *.instructions.md files, plus skill descriptions.
  3. Conversation history: everything said so far, or a summary of it after compaction.
  4. Implicit context: the open file, your selection, current errors, Git state.
  5. Explicit references: what you attached with #.
  6. Tool outputs: file reads, search results, terminal output, test logs.
Tidbit

Psychologist George Miller's 1956 paper "The Magical Number Seven, Plus or Minus Two" argued that human working memory holds only a handful of items at once. Models can hold vastly more, but they share our weakness for losing track of what's in the middle. That's the next chapter.

Chapter 07 · Part 1

Context rot & hygiene

A 1M-token window is capacity, not a target. Quality drops as the window fills, long before it's full.

Context rot

Part 1 · Step 5

The measurable drop in a model's quality as its input grows, even on simple tasks.

In Chroma's 2025 study of 18 frontier models, every model did worse as input length increased. Three things drive it:

  • Lost in the middle. Models use information at the start and end of the context better than information buried in the middle. In a long session, your early instructions are the middle.
  • Distractors. Similar-but-wrong content, such as an old stack trace or the previous version of a file, actively misleads.
  • Weaker reasoning. Even when the model can find the right fact, it reasons over it less well in a long input.

What rot looks like in Copilot

Part 1 · Step 5
  • It forgets a rule it followed an hour ago.
  • It reintroduces a bug it already fixed.
  • It rereads the same files.
  • It contradicts its own plan.
  • It invents a file or method name.
Tidbit

Humans show the same U. In memory experiments from the 1960s, people recalled the first words of a list (the primacy effect) and the last words (the recency effect) far better than the middle. It's called the serial-position effect. "Lost in the middle" is the model version of it.

Reading the ring

Rule of thumb
RingStateMove
under ~40%FocusedKeep going.
around 60%Drifting/compact with a focus, or push noisy work into a subagent.
around 90%RotNew session. Carry over a plan file or a five-line summary, not the chat.

These thresholds are a rule of thumb, not an official limit. Watch the behavior above, not just the number. VS Code also auto-compacts near the limit.

Chapter 08 · Part 1

Plan, checkpoints, Git

Think before you build, and know exactly which undo button covers what.

Plan

Part 1 · Step 6

An agent that researches the codebase, asks clarifying questions, and writes a step-by-step plan before any code changes.

Run /plan …. It asks things like "hourly granularity, or every three hours?" and "which API endpoint?". The result is stored in session memory as plan.md (Chat: Show Memory Files). Then you choose Implement (normal approvals) or Start with Autopilot.

A plan file is externalized memory. It survives compaction and new sessions, because it's a file, not a chat message. That makes it the best thing to carry into a fresh session when the old one starts rotting.

Analogy

Measure twice, cut once. Plan is the measuring. It costs a few minutes and saves you from an agent confidently building the wrong thing across twelve files.

Trap

Approving a plan is not approving tool actions. Autopilot auto-approves edits and terminal commands. Use it only where hooks and checkpoints have your back. Your org can switch it off.

Checkpoints

Part 1 · Step 7

Automatic snapshots of your workspace files and chat history at each request, so you can roll back what the agent changed.

Hover a request and choose Restore Checkpoint. Changed your mind? Redo. You can also Fork Conversation from any checkpoint to try another approach.

Analogy

A lead climber clips the rope into a bolt every few metres. If they fall, they only drop back to the last clip, not to the ground. Checkpoints are those clips. But a clip can't catch a rock you already knocked down onto someone below.

What a checkpoint can't undo

Part 1 · Step 7
ActionCheckpointGit
Files the agent editedRestoresIf committed
Chat historyRestoresNo
Terminal commands (deleted files, installs, DB changes)NoOnly tracked files
Network calls, deploymentsNoNo
Pushed commitsNoRevert, visibly

Checkpoints are short-term AI undo. Git is long-term history.

Tidbit

In July 2025 a widely reported incident saw an AI coding agent on Replit delete a company's production database during an explicit code freeze, then give a misleading account of what it had done. No editor undo button reaches a production database. That's exactly the kind of action Part 2's hooks exist to block before it happens.

Chapter 10 · Part 2

Instructions & skills

Always-on rules for everything, and on-demand know-how for some things.

Always-on instructions

Part 2.1

.github/copilot-instructions.md is added to every request in the workspace.

/init inspects your project and writes a first draft with build commands and conventions. Then edit it and add one rule your team really cares about, for example "Use java.time, never java.util.Date." Check it was used by expanding References under any reply.

Keep it short. Every line is paid for on every turn and competes for the model's attention. Ledgerly's says, among other things, "money is BigDecimal" and "do not add new dependencies".

Analogy

Instructions are the one-page "how we work here" sheet taped next to every desk. Useful precisely because it's one page. Nobody reads a taped-up 40-page handbook.

Agent Skills

Part 2.2

A folder with a SKILL.md and optional scripts and references. Copilot sees only its name and description until a task matches.

Analogy

A library doesn't pile every book on your desk. It gives you a card catalog: a short card per book. You flip through the cards, and only fetch the book whose card matches what you need. Then you only open the appendix if the chapter sends you there. A skill's description is its catalog card.

The description is the trigger

Part 2.2

Copilot decides whether to load a skill from its description alone, so write it like a search result that says what and when:

name: ascii-weather-art
description: Renders weather conditions as colorful ASCII-art banners in Java
  console output. Use when asked to make the CLI/console output prettier, more
  readable, or more fun, or when printing current weather or forecasts.
  • Say what it does in the first clause, and when to use it after "Use when…".
  • Use the words people actually type ("prettier", "console output"), not internal jargon.
  • Every skill is also a slash command: /ascii-weather-art add a STORM test case.
  • Same folder works in VS Code, Copilot CLI and the GitHub Copilot app. Personal skills live in ~/.copilot/skills/.
Try it

/create-skill a skill that explains our team's Maven multi-module conventions. Then write a prompt that should trigger it without naming it, and check References.

Tidbit

Progressive disclosure is an old user-interface design principle: show the essentials first and reveal detail on request, like an "Advanced settings" button. Skills apply it to an AI's attention instead of a human's.

Chapter 11 · Part 2

Hooks

Instructions are requests. Hooks are code that runs every time, at fixed points, and can say no.

Hooks

Part 2.3

Commands the harness runs at lifecycle events. They see the event as JSON, and they can log it, add context, or block the action.

Analogy

A sign saying "please pay your fare" is an instruction. A turnstile is a hook. It doesn't care how persuasive you are, how urgent your train is, or that you've "already paid in a previous message". No valid ticket, no entry.

How a guardrail hook works

Part 2.3

The hook file is only a pointer. All the logic lives in the script:

{
  "hooks": {
    "PreToolUse": [{
      "type": "command",
      "command": "bash .github/hooks/scripts/guardrails.sh",
      "windows": "powershell -NoProfile -ExecutionPolicy Bypass -File .github\\hooks\\scripts\\guardrails.ps1",
      "timeout": 10
    }]
  }
}
  1. The harness pipes the pending tool call to the script as JSON on stdin: tool_name, tool_input, and so on.
  2. The script checks it against its rules: rm -rf, git push, deploys, edits to .github/hooks.
  3. To block, it prints a deny decision with a reason and exits with code 2. Exit 2 means "block, and tell the model why". The model reads the reason and adapts, usually to mvn clean instead of rm -rf target.
Tidbit

Agents can't edit their own guardrails because the guardrail script also blocks edits to .github/hooks. It protects itself. That's the difference between a rule and a lock: you can argue with a rule.

The class hooks

Try it

Tail the timeline in a second terminal (tail -f .github/hooks/logs/timeline.log), then ask: The build is messy. Run rm -rf target and rebuild. Watch for ⛔ BLOCKED. Then try to talk the agent into deleting the guardrail.

Hooks are code with your permissions

Security
Trap

A hook runs whatever its script says, as you. A malicious repo could ship a hook that uploads your SSH keys. Review hook scripts before trusting a workspace, exactly as you'd review a build script. Workspace hooks only run in trusted workspaces, and your org can restrict which hooks run.

Debug them in the Output panel under GitHub Copilot Chat Hooks, and list discovered hook files with Chat: Configure Hooks or /hooks. Always test a hook in the harness you'll run it in.

Tidbit

On August 1, 2012, Knight Capital lost about $440 million in 45 minutes after a deployment left old trading code active on one of its servers. A rule that says "agents never deploy" is cheap. A hook that enforces it is cheaper than finding out the hard way.

Subagents

Part 3.2

A worker agent that gets a fresh context, does one job, and returns only its result to the agent that started it.

Analogy

A Formula 1 pit stop takes under three seconds because about 20 people work in parallel, each with exactly one job: one wheel gun, one jack, one tyre. The race engineer doesn't change tyres. They get a radio message: "done, all four". That's a coordinator with subagents.

Way 1: ad hoc, from the chat box

Part 3.2

Any agent with the agent tool (the built-in Agent has it) starts subagents when you ask. Each one shows up as a collapsed tool call; click it to see the exact prompt the parent wrote, its tool calls and its result.

Use three subagents in parallel to review src/main/java without editing anything:
one for calculation bugs, one for security issues, one for missing test coverage.
Then merge their findings into one table sorted by severity.
Trap

A subagent doesn't inherit your conversation. "Look into rounding" gets a vague answer. Write the task like a ticket: the goal, what it may touch, and what to return. "Do not change files. Return a table of file:line and the rounding technique used."

Way 2: declared in agent files

Part 3.2

When a workflow is worth repeating, encode it. A coordinator and a worker are two .agent.md files:

FrontmatterEffect
tools: ['agent', …]Lets this agent start subagents at all.
agents: [...]Allow-list of which agents it may start. ['*'] any, [] none. Names are case-sensitive.
user-invocable: falseHidden from the dropdown, still callable as a subagent. For workers.
disable-model-invocation: trueThe reverse: humans can pick it, other agents can't call it. For the Code Reviewer.
model:Per-agent model. Cheap and fast for recon, strong for the lead, a different family for review.
hooks:, handoffs:Agent-scoped hooks (Local only) and the buttons shown when it finishes.

Subagents can start their own subagents only if chat.subagents.allowInvocationsFromSubagents is on (off by default, up to five levels). Keep chains shallow: each level is another context you can't see and another bill.

Tidbit

Anthropic's 2025 write-up of its multi-agent research system reported that a lead agent with parallel subagents beat a single agent by about 90% on its internal research benchmark, and used roughly 15 times the tokens of a normal chat. Parallel agents buy speed and breadth, and you pay for both.

Handoffs

Part 3.6

Buttons under an agent's final reply that switch to the next agent, carrying the conversation and a pre-filled prompt.

Analogy

In a relay, the baton has to change hands inside a 30-metre exchange zone. Pass it outside the zone and the team is disqualified, however fast the runners. A handoff is a deliberate exchange zone: the work only moves to the next stage when a human clicks the button.

Inside the Agent Squad

One prompt, "Get the nightly batch audit-ready", and six agents with carefully limited powers.

Least privilege

Part 3.3

Give every agent the smallest set of tools that lets it do its job, and nothing more.

The recon workers only get read and search. They can't edit, even if a confusing file or a prompt injection tells them to. Only the Test Engineer and the Tech Lead have edit, and the Tech Lead alone is meant to touch production code. If one agent goes wrong, the damage is limited to what it was allowed to do.

Look closely

The Test Engineer's "tests only" rule lives in its prompt, not its tool list: it has edit like the Tech Lead. That's a suggestion, not a lock. To enforce it, add a PreToolUse hook that denies edits outside src/test. Spotting gaps like this is the point of reading agent files.

Analogy

A hotel key card opens your room, the gym and the lift to your floor. Not the other rooms, not the safe. If you lose it, the hotel's exposure is one room. An agent with every tool is a master key.

Tidbit

The principle was written down by Jerome Saltzer and Michael Schroeder in 1975, in "The Protection of Information in Computer Systems": every program and user should operate with the least set of privileges necessary to complete the job. It's 50 years old and it fits agents perfectly.

The run, phase by phase

Part 3.4
  1. Recon, in parallel. The Tech Lead launches Bug Hunter, Security Auditor and Java Modernizer in one step. The timeline shows three 🤖 ┌ subagent START lines within a second or two. Each has a credit-usage pill.
  2. Skills load. Expand a subagent: you'll see money-handling read and find-money-smells.sh run.
  3. Red first. The Test Engineer writes tests that fail for the right reason and runs mvn -q test.
  4. Green. The Tech Lead fixes the production code.
  5. Quality gate. If it tries to finish while tests are red, the Stop hook says no: 🔁 quality gate RED, and it keeps working.
  6. Handoff. Two buttons: independent review, or draft the PR.

The quality gate

Part 3.4

A Stop hook that runs mvn test when the Tech Lead tries to finish, and sends it back to work if anything is red.

The model decides when it thinks it's done. The hook decides when it is done. That's a definition of done the model can't talk its way past.

Tidbit

The pilot's checklist was born from a crash. In 1935 Boeing's Model 299 prototype went down on a test flight because the crew forgot to release a control lock. The plane wasn't "too much airplane to fly"; it was too much to remember. The fix was a short checklist, and the aircraft became the B-17. A Stop hook is a checklist the agent can't skip.

Test-driven: red, then green

Part 3.4

Writing the failing test first proves two things the final green run can't: that the bug is real, and that the test would catch it if it came back. A test written after the fix might pass for the wrong reason. Kent Beck popularized this as red, green, refactor in Test-Driven Development: By Example (2002).

Trap

Ledgerly's original four tests all pass. They test the happy path, not the money. "Tests are green" only tells you the tests you wrote agree with the code you wrote.

An independent reviewer

Part 3.6

The Code Reviewer has disable-model-invocation: true, so the Tech Lead can't call it as a subagent. It isn't marking its own homework. For a truly independent opinion, pin it to a different model family with model:.

Tidbit

Researchers (Panickssery, Bowman and Feng, 2024) found that language models used as judges can recognize their own writing and tend to rate it higher. Reviewing with a different model family is a cheap way around that bias.

Chapter 14 · Part 3

The five Ledgerly bugs

Every one of them compiles, passes the original tests, and would make a banking auditor wince. Here's what's actually going on.

1 · The vanishing penny

99.99 → 100.00
Code
InstallmentPlanner rounds 100 ÷ 3 to 33.33 and repeats it three times.
Why
Rounding each part separately loses the remainder. Three × 33.33 is 99.99.
Fix
A lossless split: BigDecimal, round each part, give the leftover cent(s) to the last installment (33.33, 33.33, 33.34).
Tidbit

In 1982 the Vancouver Stock Exchange launched an index at 1,000. Its software truncated the value to three decimals thousands of times a day, and 22 months later the index read about 520 while the market had risen. Recalculated properly, it was about 1,098. Tiny rounding errors compound.

2 · The interest that wasn't

0.0 → 12328.77
Code
principal * (rate / 100) * (days / 365), with days an int.
Why
Integer division: 90 / 365 is 0 in Java, so the whole product is zero. 1,000,000 × 5% × 90/365 should be 12,328.77.
Fix
BigDecimal arithmetic, divide last, with an explicit scale and RoundingMode.
Tidbit

Never build a BigDecimal from a double. new BigDecimal(0.1) is exactly 0.1000000000000000055511151231257827021181583404541015625, because 0.1 can't be stored exactly in binary. Use new BigDecimal("0.1") or BigDecimal.valueOf(0.1).

3 · Settling on a Sunday

Sun 2026-10-11 → Mon 2026-10-12
Code
Adds two calendar days to Thursday (Saturday), then bumps Saturday by one day (Sunday).
Why
T+2 means two business days. Thursday + 2 business days is Monday. The code also uses the legacy Date, Calendar and a shared static SimpleDateFormat, which isn't thread-safe.
Fix
java.time.LocalDate, skipping Saturday and Sunday one day at a time (and, in real life, bank holidays).
Tidbit

US equities moved from T+2 to T+1 settlement on May 28, 2024. Settlement rules change, which is one more reason to keep them in one well-tested place.

4 · Charged twice

3 → 2
Code
Payment overrides equals() by id but not hashCode(). The de-duplicator puts payments in a HashSet.
Why
A HashSet checks hashCode() first. Two "equal" payments with different hash codes land in different buckets and are never compared, so the duplicate survives.
Fix
Override hashCode() consistently, or make Payment a Java 17 record, which generates both correctly. (A record compares all fields, so decide what "same payment" means first.)
Tidbit

"Always override hashCode when you override equals" is a rule in Joshua Bloch's Effective Java. In payments the deeper fix is an idempotency key: the gateway sends a unique id per payment attempt, and you refuse to process the same key twice.

5 · Secrets in the logs

4400-1234-5678-9012 → ****9012
Code
FxConverter hard-codes an API key ("move to the vault before go-live", ticket opened 2019) and prints it, with the full account number, on every conversion. Money is a double.
Why
Logs get shipped, indexed and kept for years by people who shouldn't see secrets or full account numbers.
Fix
Read the key from the environment or a vault, never log it, and mask account numbers to the last four digits.
Tidbit

Card-industry rules (PCI DSS) cap what you may display of a card number at the first six and last four digits. Showing only the last four, as Ledgerly's fix does, is the common safe default.

Money is BigDecimal

money-handling skill

Three of the five bugs come from treating money as a double. The squad's money-handling skill writes down the rules: BigDecimal built from strings, an explicit scale, RoundingMode.HALF_EVEN, lossless splits, and currency kept next to the amount (record Money(BigDecimal amount, Currency currency)).

Tidbit

HALF_EVEN is "banker's rounding": a value exactly halfway rounds to the nearest even digit (2.5 → 2, 3.5 → 4). Always rounding halves up adds a tiny upward bias across millions of transactions; rounding to even cancels it out on average. It's also the default rounding mode in the IEEE 754 floating-point standard.

Chapter 15 · Part 3

Prove what happened

"It worked" is a claim. Logs are the evidence. Four lenses on the same run.

Trust, but verify

Part 3.5

Every agent run leaves a trail you can inspect: what it read, what it ran, which skills loaded, how many tokens each step cost.

Analogy

Every airliner carries a flight data recorder. Nobody reads it on a good day, but when something goes wrong it's the only thing that can say what really happened, not what the crew remembers. Agent logs are your flight recorder. Read them even when the run "worked".

Tidbit

"Black boxes" are painted bright orange so they're easy to find in wreckage.

① Agent Debug Logs

Part 3.5

In the Chat view use … → Show Agent Debug Logs, or run Developer: Open Agent Debug Logs. It lists every tool call, model request, skill and instruction discovery, and hook run. The Agent Flow Chart draws the coordinator fanning out to subagents, with tokens and seconds per step. The Summary totals tool calls, tokens, errors and duration.

Empty panel?

Agent Debug Logs are experimental and must be switched on, and they only capture from that moment. Ledgerly's .vscode/settings.json does it for you. Elsewhere: Settings (⌘, / Ctrl+,), search agentDebugLog. If it doesn't show up (a current UI bug), open Settings (JSON) and add "github.copilot.chat.agentDebugLog.fileLogging.enabled": true, reload the window, and run again.

② Ask the logs

The Chat Debug view (/debug) shows the raw prompt: find your skills list, instructions and the SessionStart context in it.
